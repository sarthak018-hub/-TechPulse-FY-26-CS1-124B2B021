1. Problem Statement and Intended Users
--------------------------------------------------------------------------------
Problem Statement:
In automotive embedded software engineering, High-Level Design (HLD) specifications formatted in accordance with the Classic AUTOSAR standard define component boundaries, port bindings, Sender-Receiver (S/R) interfaces, Client-Server (C/S) operations, signal routing, and timing constraints. These documents are extensive (often dozens of pages), semi-structured, and dense with technical tables. Manual review by systems architects is labor-intensive, error-prone, and slow. During Engineering Change Notices (ECNs), subtle breaking interface mismatches (such as renamed network signals, removed ports, data type mismatches across the Runtime Environment, or orphaned interfaces) frequently pass through manual reviews undetected, causing costly integration bugs in later Hardware-in-the-Loop (HIL) testing or vehicle integration phases.

Intended Users:
1. Automotive Systems Architects & Software Leads: Conducting design reviews, verifying interface compatibility across ECU revisions, and auditing ISO 26262 functional safety constraints.
2. Embedded Software Engineers & Developers: Querying component interfaces, execution periods, runnable entities, and CAN-FD/LIN signal mappings.
3. Test & Validation Engineers: Formulating Hardware-in-the-Loop (HIL) test cases mapped to functional flows and Diagnostic Trouble Code (DTC) matrices.
4. Quality & Governance Auditors: Conducting traceability audits with verified citations and immutable compliance logging.

4. Implementation and Configuration
--------------------------------------------------------------------------------
End-to-End Workflow:
Step 1: Ingestion & Structural Parsing
The raw 14-page PDF is loaded. PyMuPDF extracts page-indexed text blocks, section headings, and metadata. Simultaneously, pdfplumber parses table bounding boxes, transforming grid layouts into Markdown tables.

Step 2: Section-Aware Chunking & Embedding
The SectionAwareChunker splits text at section header boundaries. Tables are kept whole or row-chunked with the header row duplicated. Chunks receive structured metadata (doc_id, version, page, section, chunk_type). Embeddings are computed using BAAI/bge-small-en-v1.5 (384 dimensions, normalized) and persisted into ChromaDB.

Step 3: Query Processing & Context Retrieval
When a user submits a query, it is encoded into a 384-dimensional dense vector. ChromaDB executes a cosine similarity search returning the top-k (k=4) chunks, optionally filtered by version label (v1/v2).

Step 4: Dual-Stage Refusal Gating
The retrieval result passes through two sequential safety gates:
- Gate 1: If maximum similarity < 0.68, the query is rejected immediately.
- Gate 2: Substantive keywords from the query are compared against retrieved context. If overlap < 35%, the query is refused with: "Not found in the provided document."

Step 5: Prompt Formulation & Generation
Retrieved chunks are placed within an untrusted <CONTEXT_CHUNKS> block. System instructions enforce strict grounding, temperature 0.1, bracketed citation format [doc_id, version, page N, section], and confidence scoring. Ollama generates the answer locally; if Ollama is unavailable, the deterministic extractive grounding engine formulates the grounded response.

Step 6: Post-Check Verification & Audit Logging
The generated answer undergoes regex validation: every cited page must exist in the retrieved chunks. Key tokens must be grounded in context. The query, retrieved chunk IDs, answer, citations, confidence score, and verification status are appended to SQLite rag_audit_log.db.

Key Pipeline Parameters:
- Chunk Size: 600 characters
- Chunk Overlap: 100 characters
- Table Header Duplication: Enabled (True)
- Vector Index Distance Metric: Cosine
- Retrieval Top-k: 4 chunks
- LLM Temperature: 0.1 (Seed: 42)
- Cosine Refusal Threshold: 0.68
- Keyword Overlap Refusal Threshold: 0.35 (35%)
- LLM Timeout: 90 seconds

7. Innovation Highlights
--------------------------------------------------------------------------------
1. Dual-Stage Refusal Gate:
   Solves the critical "silent hallucination" failure mode in automotive RAG by pairing cosine
   similarity thresholding (0.68) with a substantive keyword overlap ratio check (35%). Out-of-domain
   questions are refused in ~104 ms without wasting inference cycles or generating misleading claims.

2. Deterministic Rule-Based Revision Comparator:
   Unlike probabilistic LLM diffing which suffers from non-deterministic omissions, our comparator
   uses 5 strict structural rules in Code/compare.py to achieve 100% defect detection recall on
   seeded changes (renamed signals, removed ports, data type mismatches, undefined component references,
   and orphan interfaces), restricting the LLM strictly to generating safety impact commentary.

3. Section-Aware Chunking with Table Header Preservation:
   Maintains architectural table integrity by parsing PDF bounding boxes via pdfplumber into
   Markdown rows and duplicating header rows across splits, preventing loss of tabular column context.

4. 100% Edge Execution on Constrained Hardware:
   The entire pipeline—vector database, dense embedding model, local LLM, and web application—runs
   within 12 GB RAM on consumer hardware with zero cloud dependencies or ongoing API costs.

9. Reflection and Conclusions
--------------------------------------------------------------------------------
Reflections:
Building this automotive HLD analysis assistant demonstrated the importance of hybrid engineering: combining deterministic algorithms with probabilistic language models. While LLMs excel at natural language synthesis and technical summarization, safety-critical tasks (such as detecting missing ports or interface breaking changes) demand deterministic rule engines that guarantee 100% recall.

A key technical challenge was handling small-collection HNSW indexing edge cases in ChromaDB, where standard filters failed on compact collections (~150 chunks). Implementing an automated numpy cosine dot-product fallback resolved the issue, ensuring robust retrieval under all conditions. Additionally, fine-tuning the dual refusal gate proved that semantic cosine distance alone is insufficient for technical acronyms; combining cosine scores with substantive keyword ratio checks proved essential for eliminating hallucinations.

Conclusions:
The AUTOSAR HLD Document Analysis Assistant achieves its objectives: reducing manual review effort, establishing a searchable architecture repository, ensuring complete component and signal traceability, and automating revision comparisons. Operating fully offline on consumer hardware, it satisfies strict automotive IP confidentiality while delivering 100% Hit@4, 0.9062 MRR, and 100% defect detection recall.
